## Раздел A. Целостность и скорость записи

### С1. [ИСПРАВЛЕНО] Нет транзакций вокруг многошаговых операций
**Статус:** исправлено в коммите `baad7f6` (2026-09-24); вместе с С3.

`Save` и `Delete` обёрнуты в транзакцию соединения (`DbConnection.BeginTransaction`, переносимо); каждый `DbCommand` внутри обязан получать `command.Transaction` (Microsoft.Data.Sqlite отклоняет команду без него). Внутренние Core-методы (`FindIdCore`/`SetAttributesCore`/`SetRatingsCore`/`SetManufacturersCore`/`ReplaceParametersCore`; `FindEquivalentCore` удалён позже, при пересмотре правила 6) получили опциональный параметр `DbTransaction?`. Поведение закреплено в регламентах: AGENTS.md («запись — в транзакции соединения»), SKILL.md («запись транзистора применяется в одной транзакции: либо целиком, либо никак»).

**Места (исходные):** `SovietTransistorsDatabase/Data/RelationalTransistorDatabase.cs:42-92` (`Save`), `:488-535` (`SetManufacturersCore`), `:584-617` (`ReplaceParametersCore`).

`Save` выполнял вставку транзистора + атрибуты + производители + параметры + ratings отдельными командами без транзакции: сбой на середине оставляет частично применённую запись. `ReplaceParametersCore` и `SetManufacturersCore` — DELETE, затем N INSERT-ов: в SQLite без явной транзакции каждый INSERT — отдельный автокоммит с собственным fsync, импорт значительно медленнее возможного, а при обрыве секция оказывается удалённой без новой.

**Решение (как было задумано):** обернуть каждую операцию уровня `Save`/`Delete` в транзакцию соединения + переиспользовать один `DbCommand` в циклах вставки. Связи: С3, С4. Проверены каскадное удаление и идемпотентность импорта (AGENTS.md правило 4).

### С2. [ИСПРАВЛЕНО] Сироты в таблице manufacturers
**Статус:** исправлено в коммите `194584f` (2026-09-24).

В конце `Save` и `Delete` — внутри их транзакций (С1) — выполняется `DeleteOrphanManufacturers`: `DELETE FROM manufacturers WHERE Id NOT IN (SELECT ManufacturerId FROM transistor_manufacturers)`; в `Delete` чистка выполняется только при реально удалённой записи. Переносимость проверена по правилам раздела «Не трогать» AGENTS.md: `NOT IN` с подзапросом работает в SQLite/PostgreSQL/MariaDB, `ManufacturerId NOT NULL` — ловушки NULL в подзапросе нет. Поведение закреплено в SKILL.md (строка `manufacturers` в таблице атрибутов). Сценарно проверено: удаление транзистора сносит бесхозные имена, общее имя выживает, пока есть хоть одна связь, замена списка (`Save`/импорт) сносит отвязавшееся имя. Связи: С1.

**Места (исходные):** `RelationalTransistorDatabase.cs:488-535`; DDL `Data/SqliteDatabase.cs:91-100`.

`SetManufacturersCore` удаляет только связи `transistor_manufacturers`; строки `manufacturers` не удаляются никогда — ни при замене списка, ни при `delete` транзистора (FK-каскад сносит только связующую таблицу). При многолетнем наполнении копятся имена заводов, отвязанные от всех транзисторов.

**Решение (как было задумано):** чистка бесхозных имён в конце `Save`/`Delete` (`DELETE FROM manufacturers WHERE Id NOT IN (SELECT ManufacturerId FROM transistor_manufacturers)` — проверить переносимость) + закрепление поведения в SKILL.md. Связи: С1.

### С3. [ИСПРАВЛЕНО] Лишние и избыточные запросы при записи
**Статус:** исправлено в коммите `baad7f6` (2026-09-24); вместе с С1.

- `Add`/`Save` — атомарный insert-if-absent: `INSERT INTO transistors (...) SELECT @... FROM (SELECT 1) AS src WHERE NOT EXISTS (SELECT 1 FROM transistors WHERE <BuildExactMatch>)`; `ExecuteNonQuery() == 0` → запись существует (`DuplicateExists`). Закрывает гонку find-then-insert, 1 команда вместо 2. Однострочная производная таблица `FROM (SELECT 1) AS src` — ради MariaDB (требует FROM при WHERE; SQLite/PostgreSQL — нет). После пересмотра правила 6 (2026-09-24) предикат тождества `BuildExactMatch` совпадает с UNIQUE `uq_transistor`; до пересмотра предикат `BuildEquivalence` (пары Г/1, К/2, ...) был строже UNIQUE.
- Повторный SELECT id после INSERT заменён новым хуком `protected abstract string LastInsertIdSql` (SQLite: `SELECT last_insert_rowid()`; при переносе — `lastval()`/`LAST_INSERT_ID()`) и методом `GetLastInsertId(connection, transaction)`. Точка переопределения зафиксирована в AGENTS.md.
- `SetManufacturersCore`: 1 DELETE + 2 подготовленных переиспользуемых команды на имя (ensure-exists через insert-if-absent + линк `INSERT ... SELECT @id, Id FROM manufacturers WHERE Name = @name`) вместо 3N+1.
- `ReplaceParametersCore`: одна подготовленная команда с параметрами, значения меняются в цикле (`DbParameter.Value`); для этого `AddParameter` возвращает `DbParameter`.

**Места (исходные):** `RelationalTransistorDatabase.cs:30-40` (`Add`), `:52-54` (`Save`), `:507-534` (N+1 производителей).

- `Save` после INSERT повторно искал id по эквивалентности — лишний SELECT.
- `Add`/`Save` — find-then-insert: при конкуренции UNIQUE-ограничение даст исключение вместо «дубликат».
- `SetManufacturersCore`: на каждое имя SELECT + INSERT + INSERT-линк = 3N+1 команд.

**Решение (как было задумано):** grouped batch + обработка конфликта UNIQUE как DuplicateExists. Реализовано через insert-if-absent + переиспользование команд (полный grouped batch не понадобился: 2 команды на имя внутри транзакции С1). Связи: С1, С13. Гарантия от эквивалентных дублей на уровне БД была открытым случаем С13 — закрыта пересмотром правила 6 (эквивалентных дублей больше не существует по определению).

## Раздел B. Подключения и накладные расходы

### С4. [ИСПРАВЛЕНО] Соединение на каждый вызов + EnsureCreated на каждый запуск + пустой Dispose
**Статус:** исправлено в коммите `0b174d1` (2026-09-24).

Соединение теперь одно на экземпляр `RelationalTransistorDatabase`: открывается лениво при первом обращении (свойство `Connection`; диалектозависимые настройки — PRAGMA — выполняются в `OpenConnection()` один раз за запуск) и закрывается в `Dispose`, который больше не пуст. `info` и импорт N записей обходятся одним соединением. `OpenExistingDatabase` (`Program.cs`) строит `SqliteDatabase` без `EnsureCreated`: команды чтения и `delete` не исполняют DDL вовсе; команды записи (`init`/`add`/`import` через `OpenDatabase`) выполняют идемпотентный DDL один раз за запуск, автосоздание базы сохранено. Поведение закреплено в AGENTS.md («Соединение БД — одно на экземпляр…»).

**Места (исходные):** `RelationalTransistorDatabase.cs` (каждый публичный метод открывал соединение), `:330-332` (пустой `Dispose`), `Data/SqliteDatabase.cs:20-29` (PRAGMA на каждое соединение), `Program.cs:455-466` (`OpenDatabase`/`OpenExistingDatabase` вызывали `EnsureCreated` при любом запуске).

Каждый метод БД открывает новое соединение; `EnsureCreated` исполняет полный DDL-скрипт (5 CREATE TABLE с гигантскими CHECK) при каждом запуске любой команды, включая `count`. `ITransistorDatabase : IDisposable` при пустом `Dispose` — интерфейс заставляет `using` там, где нечего освобождать. `info` открывает 5 соединений на один вызов (`FindId` + `GetAttributes` + `GetManufacturers` + `GetParameters` + `GetRatings`, `Program.cs:291-354`). Импорт N записей = 2N+ подключений.

**Решение:** одно соединение на экземпляр `RelationalTransistorDatabase` (или на время команды) + `EnsureCreated` только при создании (`init`, команды записи). Это же упрощает транзакции из С1. Связи: С1, С5.

### С6. [ИСПРАВЛЕНО] Семь точек синхронизации при добавлении одного параметра
**Статус:** исправлено в коммите `73216e5` (2026-09-24); вместе с С7-С9.

`ParameterInfo` теперь несёт декларативную спецификацию `ConditionSpec` (`Domain/ParameterConditions.cs`: `ConditionKey`/`ConditionKeys`/`ConditionVariant` — обязательные/опциональные ключи; именованные спеки в `ConditionSpecs`) и `ValueCeiling` (потолок значения). Из каталога генерируются: проверки C#-валидатора (одно сообщение условий на параметр), раздел help (`DescribeParameters()` в Program.cs), список полей jsonc (`TransistorJsoncReader.ParameterFields`) и CHECK-ограничения `electrical_parameters` (`Data/ElectricalParametersDdl.CreateTableSql`, компонуемый в `SqliteDatabase.CreateTableSql`). Ручная синхронизация осталась только для SKILL.md (человекочитаемый регламент). Тесты переписаны под спеки (269 тестов).

**Места (исходные):** `Domain/ElectricalParameters.cs:55-105` (каталог), `:125-232` (валидатор), `Data/SqliteDatabase.cs:118-204` (три CHECK), `Program.cs:620-631` (help), `.kilo/skills/soviet-transistors-database/SKILL.md` (таблица кодов).

Добавление нового кода параметра требует синхронных правок: (1) `ElectricalParameterCatalog.All`; (2) возможно, нового `ConditionRule` + switch-кейс валидатора; (3) хвостовых проверок Rg/Rbe/Ib/Freq; (4) трёх CHECK в DDL; (5) help-текста; (6) SKILL.md; (7) возможно, новых колонок условий. AGENTS.md правило 1 требует ручной синхронизации C# ↔ SQL — это главный источник регресса проекта.

**Решение:** сделать `ParameterInfo` декларативной спецификацией условий (обязательные/опциональные/запрещённые ключи, границы), из которой генерируются: проверки C#-валидатора, текст help и SQL CHECK (DDL — C#-строка, можно собирать программно в переопределении `CreateTableSql`). Ручная синхронизация исчезает как класс, CHECK в БД сохраняется. Связи: С7, С8, С9, С10, С25.

### С7. [ИСПРАВЛЕНО] Дубли внутри C#-валидатора параметров
**Статус:** исправлено решением С6 (2026-09-24): варианты условий описываются переиспользуемыми `ConditionVariant`-ами спеки; неверная комбинация даёт ровно одно сообщение («условия — {варианты}; задано: {фактически заданные}»).
**Места:** `Domain/ElectricalParameters.cs:154-158` (`PairUkeIkOrUkbIe`), `:194-201` (`PairPlusFrequency` копирует ту же логику), `:213-220` (хвостовые проверки перекрываются со switch-кейсами).

### С10. FET-параметры против фиксированной модели условий
**Места:** регламент SKILL.md («напряжение отсечки, крутизна, начальный ток стока пока не поддерживаются — коды обсуждаются»), `Data/SqliteDatabase.cs:102-204` (колонки и CASE только под биполярные условия), `Domain/ElectricalParameters.cs:108-123` (`ElectricalParameter` с фиксированными Uke..Temp).

Модель жёстко привязана к биполярным условиям (Uke/Ukb/Ueb/Ik/Ie/Ib). Полевые параметры требуют новых условий (Uзи, Iс, S...), то есть новых колонок + расширения всех CASE-монолитов + валидатора + каталога + help + SKILL. Каждый «пакет» полевых параметров умножает самую хрупкую часть схемы.

**Решение:** поскольку миграции не поддерживаются и база пересоздаётся импортом, сейчас дешевле всего либо условия как пары (ключ, значение), либо генерация из спецификации С6. Отложить — CASE-таблицы вырастут ещё на ~10 кейсов с дублями. Связи: С6, С8.

### С11. Непоследовательная глубина дубля валидации
**Места:** `Data/SqliteDatabase.cs:50` (`chk_letters CHECK (Letters <> '')` — слабее домена, требующего 1-2 заглавных кириллических), `:82-88` (`chk_any_attribute`), `RelationalTransistorDatabase.cs:422-427` (`HasAnyAttributeField` — та же проверка третьей копией).

`chk_letters` — единственное место, где SQL-зеркало слабее C#-валидатора; список из 15 полей атрибутов перечислен в трёх местах (SQL CHECK, `HasAnyAttributeField`, валидатор+JsoncReader). Вероятно, осознанное послабление (CHECK в SQLite не умеет регулярки для кириллицы) — тогда зафиксировать комментарием; список полей атрибутов свести к одной константе.

**Решение:** комментарий-обоснование для `chk_letters`; единый источник списка полей атрибутов. Связи: С6.

## Раздел D. Схема БД и слой данных

### С12. [ИСПРАВЛЕНО] Разнобой кодирования NULL/булевых в схеме
**Статус:** исправлено (2026-09-24).

`Assembly` стал INTEGER NOT NULL 0/1 (CHECK `Assembly IN (0, 1)`) — как остальные булевы схемы (`EsdSensitive`, `MilitaryGrade`, `RadiationHardened`); строка-флаг «С» из схемы исчезла. Сенти́нелы убраны: фильтры `Query` для `Assembly`/`Modification`/`ChipVariant` — простое равенство (фильтр всегда задаёт конкретное значение, COALESCE ничего не добавлял), а сравнение опциональных колонок в предикате тождества — единый NULL-безопасный паттерн `(col = @p OR (col IS NULL AND @p IS NULL))`, применявшийся там и раньше; для `Assembly` он не нужен — колонка NOT NULL. `COALESCE` в DML больше не используется. Конвенция закреплена в AGENTS.md (правило 8) и doc-комментарии `RelationalTransistorDatabase`. Формат jsonc и вывод CLI не изменились; рабочая база пересоздана импортом.

### С13. [ЗАКРЫТО] Эквивалентность материалов не enforced на уровне БД
**Статус:** закрыто пересмотром правила 6 (2026-09-24), без изменения схемы.

Обозначение стало точным ключом записи: `КТ312` и `2Т312` — отдельные записи с собственными данными, «эквивалентных дублей» больше не существует по определению, и UNIQUE `uq_transistor` теперь гарантирует ровно то, что требует регламент. Предикат тождества (`BuildExactMatch`) совпадает с UNIQUE и использует индексные сравнения; COALESCE-предикаты остались только в `BuildMaterialCounterpartMatch` (подсказка `find`, не критичный путь). Равнозначность Г/1, К/2, А/3, И/4 осталась физической характеристикой материала: фильтр `list --material` группирует оба символа, `find` при отсутствии точной записи подсказывает парную (`FindMaterialEquivalents`). Регламенты (AGENTS.md правило 6, SKILL.md, README) синхронизированы. Предложенное ниже решение (канонический kind + отдельная колонка символа) не понадобилось.

**Места (исходные):** `Data/SqliteDatabase.cs:53` (`uq_transistor UNIQUE (Material, ...)`), `RelationalTransistorDatabase.cs:386-392` (`FindIdCore`: `LIMIT 1` без ORDER BY), `:642-664` (`BuildEquivalence` с COALESCE-предикатами).

Регламент гарантирует «1Т402Ж найдёт ГТ402Ж», но это только логика приложения: UNIQUE допускает сосуществование ГТ402Ж и 1Т402Ж (защита — insert-if-absent из С3; предикат эквивалентности строже UNIQUE, поэтому гонка дублей закрыта на уровне приложения, но не БД). Если дубликаты появятся, `LIMIT 1` без ORDER BY вернёт недетерминированную запись. COALESCE-предикаты (`COALESCE(Assembly,'')=...`, `COALESCE(Modification,-1)=...`) не используют UNIQUE-индекс — эквивалентный поиск деградирует до скана, при тысячах записей уже заметно.

**Решение:** хранить канонический вид материала (kind), а «символ как в источнике» — отдельной колонкой для отображения: UNIQUE тогда реально препятствует эквивалентным дублям, запросы упрощаются до индексных сравнений. Меняет документированное «хранится как в обозначении» — решение нужно согласовывать и фиксировать в регламенте. Связи: С3, С12.
