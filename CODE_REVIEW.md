### Н1. Импорт применяет запись с ошибочной секцией

**Места:** `SovietTransistorsDatabase/Import/TransistorJsoncReader.cs:184-201` (`ReadEntry`), `SovietTransistorsDatabase/Program.cs:193-217` (`CmdImport`).

`ReadEntry` добавляет запись в `result.Entries`, даже если её секция целиком отвергнута из-за ошибок: `ReadAttributes`/`ReadParameters`/`ReadRatings` при проблемах возвращают `null` («не менять»), и запись уходит в `CmdImport` как обозначение + остальные секции. Следствия:

- **новый** транзистор из ошибочной записи вставляется в базу «голым» обозначением без отвергнутой секции (например, без параметров), хотя файл заведомо ошибочен;
- запись с корректным обозначением и испорченной секцией `parameters` обновит атрибуты/производителей/предельные данные, а параметры не тронет — частичное применение записи при том, что правило 4 AGENTS.md защищает от частичного стирания только в пределах одной секции;
- счётчик «корректных записей» включает такие записи, а dry-run печатает их как `(проверка) КТ315Б` без пометки, что секция отвергнута — пользователь может считать проверку успешной, хотя exit-код 1.

Асимметрия: ошибки разбора ключей записи (`CheckEntryKeys`) и обозначения отвергают запись целиком, ошибки значений секций — нет. Защита «секция не применяется» реализована корректно для существующих записей; проблема в том, что сама запись всё равно применяется.

**Решение (на выбор, зафиксировать в SKILL.md/AGENTS.md):** либо не добавлять запись в `Entries` при любой ошибке её секций (файл целиком валиден — применяется, нет — не применяется вовсе), либо оставить текущее поведение осознанно, но тогда помечать такие записи в dry-run и в счётчиках (например, «частично»). Первый вариант проще и не имеет известных контраргументов.

### Н2. Позитивность значений и условий параметров не отражена в SQL CHECK

**Места:** `SovietTransistorsDatabase/Data/ElectricalParametersDdl.cs:32-52` (`AppendValueBounds`), для сравнения `Data/SqliteDatabase.cs:130-145` (`chk_ratings`).

`chk_param_value` проверяет только наличие/соотношение границ, но не `ValueMin > 0`/`ValueMax > 0`; positivity условий (`Uke > 0`, `Freq > 0`, …) в CHECK тоже нет. C#-валидатор всё это проверяет (`ElectricalParameters.cs:119-133`), но запись извне (другой клиент, ручной SQL) беспрепятственно сохранит отрицательные значения. Непоследовательно с `maximum_ratings`, где positivity каждого поля зеркалирован в `chk_ratings`. Замечание об исключении в AGENTS.md (правило 1) касается только `chk_letters` — здесь нет документированного обоснования послабления.

**Решение:** добавить в `chk_param_value` ветку `ValueMin > 0 AND (ValueMax IS NULL OR ValueMax > 0)`, а в `chk_param_conditions` — positivity заданных условий (`(Uke IS NULL OR Uke > 0) AND …`). Оба генерируются из каталога, ручной синхронизации не появится. Дёшево, пока миграции не поддерживаются; при переносе на PostgreSQL/MariaDB переносимость предиката не вызывает вопросов.

### Н3. ValueCeiling проверяет только ValueMin

**Места:** `SovietTransistorsDatabase/Domain/ElectricalParameters.cs:122-126`, `SovietTransistorsDatabase/Data/ElectricalParametersDdl.cs:45-46`.

И валидатор, и генерируемый CHECK сравнивают с потолком только нижнюю границу: `ValueMin <= ceiling`. Сегодня потолок есть только у `Kpd` (направление «не менее», `max` запрещён), поэтому дефект латентный. Но стоит добавить потолок параметру с `BoundDirection.AtLeastOrRange` (`h21e`/`h21b`) — и верхняя граница диапазона уйдёт за потолок без диагностики в обоих слоях.

**Решение:** проверять также `ValueMax`: C# — `parameter.ValueMax is double maxV && maxV > ceiling`; DDL — `AND (ValueMax IS NULL OR ValueMax <= <ceiling>)`. Согласованно в обоих местах, чтобы не плодить новый вариант «SQL слабее домена».

### Н4. `--db=` (пустое значение) не отвергается

**Места:** `SovietTransistorsDatabase/Program.cs:35-38` (разбор `--db=`), `:463-466` (`ResolveDatabasePath`).

`--db=` даёт `dbPath = ""` — не null, поэтому `ResolveDatabasePath` не подставляет значение по умолчанию/переменную окружения. Команда чтения напечатает «база данных не найдена» с пустым путём; команда записи создаст базу с пустым `DataSource` в строке подключения (SQLite трактует это как ephemeral/`:memory:`-подобное поведение в зависимости от версии) — файл в ожидаемом месте не появится, и последующий `list` по тому же `--db=` его «не найдёт». Соседние опции с явной валидацией значений (`--limit`, `--letters`) отвергают пустоту сразу.

**Решение:** в точке разбора отвергать `--db`/`--db=` с пустым значением: «после --db ожидается непустой путь к файлу базы», exit 1.

### Н5. Косметика help и DescribeParameters

**Места:** `SovietTransistorsDatabase/Program.cs:613-614`, `:645`.

1. В `DescribeParameters()` при `info.Unit is null` строка `" (не более {Fmt(ceiling)} {info.Unit})"` даст висячий пробел и отсутствие единицы («не более 100 »). Сегодня потолок только у `Kpd` (единица «%»), так что латентно; поправка очевидна (`unit`-переменная уже вычислена строкой выше).
2. В `PrintHelp` строка «Команды list/info/find/count/delete работают только с существующей базой» стоит внутри секции «Опции:» между `--dry-run` и «Фильтры list» — содержательно это не опция; логичнее отдельной строкой после блока опций.

## Проверено и замечаний не вызвало

- Транзакции вокруг `Save`/`Delete`, `command.Transaction` у всех команд внутри, чистка сиротов производителей в той же транзакции (С1, С2 — регрессий нет).
- `InsertTransistorIfAbsent` — предикат совпадает с `uq_transistor`; `last_insert_rowid()` сразу после INSERT в транзакции (С3).
- Одно ленивое соединение на экземпляр, `Dispose` закрывает; `OpenExistingDatabase` без DDL для команд чтения (С4, С5).
- `RowReader` с `GetOrdinal` по центральной спецификации колонок; SELECT собирается из тех же массивов (С14).
- NULL-безопасный предикат тождества без сентинелов; булевы INTEGER 0/1; `Assembly` NOT NULL (С12, правило 8).
- Спецификации условий (`ConditionSpec`/`ConditionVariant`) корректны: проверка `Required.Contains(key) != set && !Optional.Contains(key)` перебирает все ключи и не пропускает лишние/отсутствующие условия; генерация CHECK из вариантов (`VariantSql` + `Forbidden`) соответствует C#-семантике, включая `PairPlusFrequency` и `FrequencyPlusOptionalUkeIk`.
- `chk_letters`-послабление и AUTOINCREMENT снабжены комментариями-обоснованиями и пунктами «Не трогать» (С11, С15).
- Парсер обозначений: все ветки ошибок с позициями, нормализация `−`/`–` → `-`, обходные случаи (0-модификация, 3-значный номер с ведущим нулём, буквы после 2-й буквы, хвост после бескорпусного) покрыты тестами.
- `help` раздел параметров генерируется из каталога; справка фильтров соответствует сообщениям ошибок (`--limit` без «2147483647»).

## Рекомендация

Из находок заслуживает немедленной работы только Н1 (поведение импорта при ошибках секций) — она затрагивает целостность данных в самом частом сценарии наполнения и должна быть решена (кодом или фиксацией в регламенте) до массового наполнения базы. Н2–Н5 — дешёвые точечные правки, можно брать по одной на сессию; Н3 и Н2 логично делать вместе с любой правкой каталога параметров. С10 (FET-условия) остаётся главным архитектурным ограничением по мере роста справочника полевых транзисторов.
