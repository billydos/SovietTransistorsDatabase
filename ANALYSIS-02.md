## Резюме

Код импортёра в целом качественный и соответствует заявленной архитектуре: реестр форматов расширяемый, ошибки — значения (`*domain.UserError`), атомарность записи («ошибка в секции — запись не применяется вовсе») реализована аккуратно, числа хранятся исходным текстом без потери точности. Юнит-тесты актуальны коду: все проходят, дословные тексты русских сообщений в тестах совпадают с текущими, при правках доменных сообщений тесты импортера сработают сторожем.

Главная активная опасность — A1: дубликаты ключей в jsonc молча игнорируются («выигрывает первый»), включая повтор ключа `transistors` или `name` в записи; yaml тот же файл отвергает. Поведение задокументировано, но для пользователя это тихая потеря данных при случайном дублировании. Второй по важности класс — латентные рассинхронизации (A2, B1): список допустимых ключей параметров генерируется из каталога `domain.AllConditionKeys`, а фактическое чтение значений в структуру захардкожено; пин-теста нет. Сейчас списки совпадают, но при добавлении нового `ConditionKey` значение станет «допустимым» и будет молча отброшено. Аналогично вручную синхронизируются `extraFields`/`ratingFields`.

Тестовая организация хорошая (reader тестируется напрямую на дереве value, фронтенды — своими smoke-сценариями), но покрытие неравномерное: 72.8% по операторам, при этом позитивный путь `readParameterItem` (условия реально попадают в структуру) не утверждается ни одним тестом — именно тот участок, что является ручной точкой синхронизации (B4). Слабо покрыты `readAttributes` (56%), `readOptionalIntField` (27%, поля `modification`/`chip` не встречаются ни в одном тесте), негативные ветки полей формы явного обозначения. Проверено и за рамками тестов: хвостовой мусор после корня hujson отвергает, yaml-якоря/теги/merge-ключ/числовые ключи обрабатываются корректно.

## A. Находки высокого приоритета

### A1. Дубликаты ключей в jsonc молча игнорируются — тихая потеря данных

**Где:** `internal/importer/value.go:36-43` (`value.has`), `internal/importer/format_jsonc.go:69` (`decodeValue`, построение `members` без детекции повторов); заявки: комментарий `format_yaml.go:14-16` и SKILL.md («повторяющиеся ключи в yaml отвергаются при разборе (в jsonc выигрывает первый)»).

`value.has` возвращает первое совпадение имени; `decodeValue` кладёт оба одноимённых ключа в `members`, но никто не сравнивает повторы. Воспроизведено зондажным тестом: `{"transistors": ["МП39"], "transistors": ["КТ315Б"]}` — второй массив полностью игнорируется, ни ошибки, ни Issue; повторный `"name"` внутри записи (`{"name": "МП39", "name": "КТ315Б"}`) — то же самое, `checkEntryKeys` не замечает дубль, т.к. имя «допустимое». Для yaml goccy отвергает повторы на этапе разбора (проверено) — асимметрия между форматами задокументирована, но у пользователя при случайном дублировании ключа (частая опечатка при ручном наборе jsonc) данные теряются без предупреждения. Контраст с AGENTS.md правилом 4 («ошибка хотя бы в одном значении — секция отвергается» — защита от частичного применения) — здесь защита не срабатывает: файл применяется, но не весь.

**Рекомендация:** при построении объекта в `decodeValue` (или проходом в `parseRoot`/`readEntry`) детектировать повтор имени и выдавать `Issue` (или `UserError`) с именем ключа и номером записи. Минимум — зафиксировать ограничение предупреждением в SKILL.md рядом с существующей оговоркой.

### A2. Чтение условий параметра захардкожено и не защищено пин-тестом против каталога

**Где:** `internal/importer/reader.go:354-368` (`readParameterItem`, явный список `Uke, Ukb, Ueb, Ik, Ie, Ib, Freq, Rg, Rbe, Temp`), `internal/importer/reader.go:55-62` (`buildParameterFields` — генерация допустимых ключей из `domain.AllConditionKeys`); инвариант AGENTS.md правило 1: «список полей секции jsonc... генерируются из каталога».

Список *допустимых* ключей растёт из каталога автоматически, а отображение ключ→поле структуры — ручное. Сейчас 9 условий + `temp` совпадают с `ElectricalParameter`, активной ошибки нет (проверено зондажем: `h21e` с `Uke/Ik/temp` читается корректно). Но при добавлении в домен нового `ConditionKey` (например, `CondRl`) ключ автоматически станет допустимым в jsonc, `readParameterItem` его не прочитает, и значение будет молча отброшено; если ключ не обязателен в `ConditionSpec`, валидация ничего не заметит — тихая потеря данных, единственное ручное звено в цепочке, которая иначе генерируется из каталога целиком (валидатор, справка, CHECK-ограничения). Позитивный путь этого маппинга не покрыт тестами (см. B4), т.е. рассинхронизация не будет поймана и тестами.

**Рекомендация:** пин-тест в importer: для каждого ключа `parameterFields` (кроме `parameter`/`min`/`max`) — round-trip «ключ в jsonc → значение в структуре `ElectricalParameter`» (можно через `domain.ConditionValueOf`); при добавлении ключа в каталог тест упадёт, пока не добавится чтение. Альтернатива — генерировать чтение условий отражением/switch'ем по `AllConditionKeys` по образцу `domain.ConditionWithValue`.

## B. Находки среднего приоритета

### B1. `extraFields` и `ratingFields` синхронизируются с доменными структурами вручную

**Где:** `internal/importer/reader.go:40-48` (списки), `reader.go:253-269` (построение `TransistorAttributes`), `reader.go:404-419` (построение `MaximumRatings`); доменные источники — `domain/attributes.go:47-59` (`AttributeFieldNames`, reflect), `domain/ratings.go:7-30`.

В БД списки полей атрибутов генерируются из `AttributeFieldNames()` автоматически, в importer — дублируются руками. Новое поле записи «подхватывается автоматически» везде, кроме импорта: здесь его придётся добавить в три места (список, построение структуры, домен). Отказ при рассинхронизации громкий («неизвестное поле» — данные не теряются), но ловится только ручным прогоном: доменный пин-тест `TestAttributeFieldNames_PinExpectedFields` importer не защищает, собственного пин-теста в importer нет.

**Рекомендация:** пин-тесты: `extraFields` (+`manufacturers`) эквивалентен `domain.AttributeFieldNames()` в нижнем регистре первых букв; `ratingFields` — именам полей `MaximumRatings` (по образцу доменного пин-теста через reflect).

### B2. Неравномерная семантика `null` и расхождение с формулировкой SKILL.md

**Где:** `internal/importer/reader.go:273-274` (`manufacturers: null` — «не менять»), `reader.go:302` и `reader.go:393` (`parameters`/`ratings` не-массив/не-объект — ошибка, включая `null`), `reader.go:241-243` (`attributes: null` — ошибка); SKILL.md, раздел формата (строка 41: «`null` — «не менять»»).

Воспроизведено: `"attributes": null` → Issue «"attributes" должно быть объектом»; `"parameters": null` → «"parameters" должно быть массивом объектов»; при этом `"manufacturers": null` внутри секции — легитимное «не менять». Само поведение консистентно с AGENTS.md правило 4 («задана — заменить целиком», null — не значение), но фраза SKILL.md «null — "не менять"» читается как применимая и к секциям целиком — пользователь, написавший `"ratings": null` по аналогии с `manufacturers`, получит неожиданную ошибку.

**Рекомендация:** уточнить SKILL.md: явно указать, что null-семантика «не менять» действует на *поля* внутри секций (и на `manufacturers`), а null у целой секции — ошибка. Либо (спорнее) поддержать null = «не менять» на уровне секций.

### B3. Issues, собранные до жёсткой ошибки корня, теряются

**Где:** `internal/importer/reader.go:80-90` (`parseRoot`).

Для `{"extra": 1}` цикл по `root.members` appending Issue про неизвестный ключ, после чего `root.has("transistors")` возвращает `UserError` «отсутствует обязательный ключ "transistors"» — результат с Issue отбрасывается (`return nil, ...`), CLI печатает только последнюю ошибку. Диагностика про `extra` пропадает; на файле с несколькими проблемами корня пользователь чинит их по одной.

**Рекомендация:** перенести проверку наличия/типа `transistors` до цикла по неизвестным ключам, либо включать собранные issues в текст `UserError`.

### B4. Пробелы покрытия юнит-тестами

**Где:** `internal/importer/*_test.go`; измерено `go test -coverprofile` + `go tool cover -func`, итого 72.8% по операторам.

Ключевое: позитивный путь `readParameterItem` — ни один тест не утверждает, что условия (`Uke`, `Ik`, `temp`, ...) реально попадают в `ElectricalParameter` (только негативные сценарии: неизвестный код, отсутствие условий) — см. A2. Далее по функциям: `readAttributes` 55.6% (нет тестов: полный валидный набор атрибутов, «неизвестное поле», невалидный элемент `manufacturers`, ошибки доменной валидации — пустая строка, годы, масса); `readOptionalIntField` 27.3% (`modification`/`chip` не встречаются ни в одном тесте); `readOptionalBool`/`readOptionalInt` 42.9%; `readCharField`/`readLettersField`/`readIntField` ~53-55% (негативные ветки формы явных полей обозначения); `yamlKeyName` 40% и `yamlToValue` 63.3% (merge-ключ `<<`, числовые ключи, якоря/теги/literal-блоки — работают, проверено, но не закреплены тестами); `describeKind` 20%. В `format_test.go` не покрыты диспатч `.json`/`.jsonc` через `ParseFile` и регистр расширения (`.JSON` — поведение есть, `strings.ToLower`).

**Рекомендация:** добавить позитивный тест чтения условий (приоритет, связан с A2), по одному негативному тесту на каждый `readOptional*`-хелпер, тест валидных атрибутов целиком, smoke на `.jsonc`/`.JSON` диспатч.

## Что сделано хорошо

- **Реестр форматов** (`format.go:13-23`): новый формат — один файл + одна запись; выбор по расширению регистронезависим, ошибки ФС отделены от `UserError`.
- **Ошибки — значения, не паника** (AGENTS.md правило 9): синтаксические ошибки обоих форматов и ошибки структуры корня заворачиваются в `*domain.UserError`; паник в пути данных нет (проверено зондажами, включая циклические yaml-алиасы — краша нет).
- **Атомарность записи** (`reader.go:146-159`): снимок `issuesBeforeSections` корректно реализует «ошибка в любой секции — запись не применяется вовсе» из AGENTS.md правило 4.
- **Числа как текст** (`value.go:23-33`, `format_jsonc.go:23` `UseNumber`): точность сохраняется до валидации, сообщения об ошибках едины для форматов; `intValue` ограничен диапазоном int32 осознанно (комментарий).
- **Читаемость семантики nil** (AGENTS.md правило 10): nil-секция ≠ пустая секция выдержана по всему пакету и закреплена тестом `EmptySections_Clear`.
- **Тестовая организация** (`reader_test.go:8-19`): reader тестируется напрямую на дереве value через конструкторы `str/num/boolean/null/arr/obj` — семантика секций не зависит от фронтендов; разделение документировано.
- **Проверенная устойчивость yaml-фронтенда**: хвостовой мусор после корня jsonc отвергает hujson; merge-ключ `<<`, числовые ключи, якоря/алиасы/теги yaml обрабатываются предсказуемо (воспроизведено, но не закреплено тестами — см. B4).

## Рекомендуемый порядок исправлений

1. **A1** (дёшево, устраняет единственную активную тихую потерю данных) — детекция дубликатов ключей в `decodeValue` + тест на дубль `transistors`/`name`.
2. **A2 + B4-позитив** (тесты до любого рефакторинга) — пин-тест «каждый ключ `parameterFields` читается в структуру» и позитивный тест условий; фиксирует самый хрупкий участок.
3. **B2** (документация) — уточнить null-семантику секций в SKILL.md.
4. **B1** (пин-тесты списков) — `extraFields`/`ratingFields` ↔ доменные структуры.
5. **B3** (мелкая правка диагностики) — не терять issues корня при жёсткой ошибке.
6. **B4-остаток и C1-C10** — по мере правок пакета; C4 (мёртвые ветки `describeKind`) уместно убрать попутно.
